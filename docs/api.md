# 2단계: 저장과 API (2026-10-10 완료 기준, 구현 전)

측정이 없는 단계라 완료 기준을 먼저 적는다. 서버는 Kotlin + Spring Boot, 저장은 PostgreSQL(Flyway 마이그레이션), SQL은 `JdbcClient`로 직접 쓴다(JPA는 쓰지 않는다. 초 단위 시계열을 배열 컬럼으로 저장하는 데 ORM이 방해가 된다).

## 저장 모델
| 테이블 | 내용 |
|---|---|
| `athlete` | id(uuid), name, gender, birth_year, weight_kg, created_at, time_zone(IANA 이름, 기본 `Asia/Seoul`, 2026-10-15 V3) |
| `athlete_threshold` | athlete_id, effective_from(date), ftp_watts, source(`manual` / `estimate`). 그 날짜의 FTP는 effective_from ≤ 날짜인 가장 최근 행 |
| `activity` | id(uuid), athlete_id, started_at(timestamptz), source(`fit` / `opendata`), source_name, sport, rec_int_secs, sample_count, duration_secs, device(manufacturer, product), crc_valid, jitter(최빈 간격 비율), power_missing, created_at. 같은 선수·같은 시작 시각은 유일(중복 업로드 거절) |
| `activity_samples` | activity_id, secs real[], power smallint[], heart_rate smallint[], cadence smallint[], distance_m real[], altitude_m real[]. 활동당 한 행. 결측은 NULL 원소 |
| `activity_metrics` | activity_id, ftp_used, np, intensity, tss, average_power, max_power, mmp jsonb(16구간), work_kj, computed_at, metrics_version(계산한 지표 코드의 버전, 지금 1). **2026-10-29 정정**: `metrics_version`은 기록만 하고 이 값을 읽어 다시 계산하는 경로는 없다(자동 재계산 없음. 처음에는 '지표 코드가 바뀌면 다시 계산해 덮어쓴다'고 적었다). 지표 계산 정의를 바꾸면 `MetricsService.METRICS_VERSION`을 올리고, 저장된 옛 버전 행을 샘플부터 다시 계산하는 도구를 그때 함께 만들어야 한다(지금은 없다. | `PUT /athletes/{id}/time-zone` | 시간대 변경 {timeZone} | 모든 활동의 지표를 다시 계산하고 {timeZone, recomputedActivities}. 모르는 이름은 400 (2026-10-15 추가). **2026-10-24 추가**: 재계산은 저장된 NP·샘플 수·기록 간격으로 IF·TSS만 다시 계산하고(샘플은 읽지 않고 NP·MMP·곡선·평균·최대·일은 그대로) 적용 FTP가 바뀐 행만 쓴다. `recomputedActivities`는 다시 계산한 활동(파워 활동) 수라 적용 FTP가 그대로인 활동도 센다. 선수 행 잠금을 상한 안에 얻지 못하면 409 `athlete_busy` |

Tomcat은 파트의 `filename`·`filename*`·RFC 2047 인코딩 단어에서 푼 이름에 NUL이 있으면 요청 해석 단계에서 거절해 400 `bad_request`(`malformed multipart request`)이고, 서버 코드까지 NUL이 오는 것은 `filename*=UTF-8''a%00b.fit; filename="ok.fit"`처럼 둘이 함께 있어 Tomcat(뒤의 filename)과 Spring(filename*)이 다른 쪽을 고를 때다 |

- **날짜 기준(2026-10-15 변경)**: 활동 날짜(적용할 FTP 찾기), 훈련 부하의 날짜 묶음, 기간 커브·FTP 추정의 기준일 창, 날짜 기본값('오늘')은 선수 시간대(`time_zone`, 기본 `Asia/Seoul`)의 현지 날짜로 센다. 그 전에는 모두 UTC 날짜라 한국에서 오전 9시 전에 시작한 라이딩이 PMC의 전날에 쌓이고 그날부터 바꾼 FTP 대신 전날 FTP로 계산될 수 있었다. 조회 요청의 `tz`는 보기만 바꾼다(저장된 TSS는 선수 시간대로 고른 FTP로 계산된 그대로). OpenData 가져오기 도구는 메타데이터 날짜가 UTC라 가져온 선수를 `UTC`로 만든다. 활동의 `startedAt`은 그대로 UTC 시각으로 저장·응답한다
  - **2026-10-24 추가: 시간대는 서버(Java)만 해석한다.** 현지 날짜와 현지 0시 경계는 모두 서버가 `java.time`으로 세고(서버를 실행하는 JDK의 tz 데이터베이스를 따른다. 규칙이 바뀐 지역은 JDK를 갱신해야 반영된다), DB(PostgreSQL)에는 시간대 이름을 넘기지 않고 서버가 계산한 순간 범위로 행만 고른다. `timeZone`과 `tz`는 Java `ZoneId.of`가 받는 이름을 모두 받는다: IANA 지역 이름(`Asia/Seoul`), `UTC`, 고정 오프셋(`+09:00`, `UTC+9`, `GMT+9`. ISO-8601처럼 +가 그리니치 동쪽이고, `Etc/GMT-9`처럼 tz 데이터베이스의 Etc 이름만 그 데이터베이스 규칙대로 부호가 반대라 UTC+9). 저장·응답에는 Java가 정규화한 이름(`UTC+09:00`, `GMT+09:00`)을 쓴다. 쿼리 파라미터 `tz`의 `+`는 URL에서 `%2B`로 보낸다(그대로 쓰면 공백으로 읽혀 400). 그 전에는 훈련 부하의 날짜 묶음과 워밍업 시작일만 SQL `at time zone`이 셌는데, PostgreSQL은 tz 데이터베이스에 없는 오프셋 이름을 POSIX 규칙(+가 서쪽)으로 읽어 `+09:00`·`UTC+9`·`GMT+9` 선수의 PMC가 오류 없이 UTC−9 날짜로 묶였고(활동에 적용할 FTP와 기간 커브 창은 원래 Java로 세서 맞았다), `EET`·`CET`는 서머타임 없는 고정 약어로 읽었으며, PostgreSQL 이미지가 모르는 옛 별칭(`US/Eastern`, `ROK` 등)은 500이었다. 저장된 TSS는 원래 Java 날짜로 고른 FTP로 계산된 것이라 다시 계산할 필요가 없다
- 인증은 2단계에서 넣지 않는다(로컬 데모). 5단계 보안 점검에서 선수 토큰(헤더)을 넣을지 정한다
- 오류 응답은 `{ "error": "<코드>", "message": "<설명>" }`
- 400 `bad_request`는 요청 형식 오류(JSON·타입 불일치·파트 누락)와 컨트롤러·서비스가 일부러 하는 입력 검사(`BadRequestException`: `every` ≥ 1, `weeks` 1~104, 조회 범위 3년 이하, 날짜 1900-01-01~2100-12-31)에만 쓴다. 코드 안의 `IllegalArgumentException`(require 실패 등 내부 버그)은 500 `internal`로 드러난다(2026-10-15 변경: 그 전에는 `IllegalArgumentException` 전체가 400이라 내부 버그가 400으로 가려질 수 있었고, 날짜 범위 검사가 없어 FTP 적용일 +300000-01-01이 500이었다)
  - **2026-10-24 추가**: 요청 형식 오류의 `message`는 예외 종류별 고정 문구다. JSON 본문 파싱 실패·필수 필드 누락 → `malformed JSON body`, 경로·쿼리 값의 타입 불일치 → `'<이름>' has an invalid value`(예: `GET /api/activities/abc` → `'id' has an invalid value`), multipart에 file 파트 없음 → `multipart part 'file' is required`, 필수 쿼리 파라미터 누락 → `'<이름>' is required`, multipart 본문 해석 실패 → `malformed multipart request`. 그 전에는 Spring·Jackson 예외 메시지의 첫 줄을 그대로 돌려줘 `java.lang.String`·`java.util.UUID` 같은 타입 이름과 요청 DTO 클래스 이름이 응답에 드러났다(500에는 스택·SQL을 숨기면서 400에는 같은 기준이 없었다). 원문은 서버 debug 로그에만 남는다. 입력 검사(`BadRequestException`)의 문구는 그대로다(예: `weeks must be between 1 and 104`). 화면은 `error` 코드로 안내 문장을 고르므로 영향이 없다
- 409 `athlete_busy`(2026-10-24 추가): 같은 선수의 다른 쓰기 요청(업로드 저장, FTP·시간대 변경, 삭제)이 선수 행(`select ... for update`)을 잡고 있어 잠금 대기 상한(`ride-insight.athlete-lock-timeout`, 기본 5초) 안에 차례가 오지 않았다. `Retry-After` 헤더(초, 상한을 올림한 값)만큼 뒤에 같은 요청을 다시 보내면 된다. 서버는 트랜잭션 단위 `lock_timeout`(PostgreSQL SQLSTATE 55P03)으로 구현했고, 같은 시작 시각의 409 `duplicate_activity`와는 `error` 값으로 구분한다. 그 전에는 잠금 대기에 상한이 없어 요청이 잠금을 쥔 쪽이 끝날 때까지 기다렸다
- 421 `host_not_allowed`(2026-10-29 추가): 요청의 Host(포트 제외)가 서버 설정 `ride-insight.allowed-hosts`(기본 `localhost,127.0.0.1,[::1]`, 대소문자는 가리지 않고 포트는 보지 않음)에 없으면 다른 필터·컨트롤러에 닿기 전에 고정 문구 `host not allowed`로 답한다(`X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, 받은 Host는 되돌려 쓰지 않음). 인증이 없는 이 API에 DNS rebinding(공격자 도메인의 DNS 응답을 짧은 TTL 뒤 127.0.0.1로 바꿔 브라우저가 같은 출처로 부르게 하는 것)으로 외부 페이지가 접근하는 것을 막는다. 그 전에는 Host를 보지 않아 `Host: evil.example`로 보낸 선수 생성이 201이었다. 웹(nginx, 8081)은 `localhost`·`127.0.0.1`이 아닌 Host와 Host 없는 요청에 응답 없이 연결을 닫는다(nginx 444). 다른 기기에서 쓰려면 그 주소를 이 목록(compose에서는 환경 변수 `RIDEINSIGHT_ALLOWEDHOSTS`)과 `web/nginx.conf`의 `server_name`에 함께 더한다(`compose.yaml` 머리 주석). compose 네트워크 안에서 `server:8080`으로 직접 부르는 요청도 421이다(nginx는 브라우저가 쓴 Host를 넘기므로 해당 없음)
- 응답 압축(2026-10-29 추가): `Accept-Encoding`에 `gzip`이 있으면 1 KB 이상 JSON 응답을 gzip으로 보낸다(`Content-Encoding: gzip`, `Vary: accept-encoding`). 1 KB 미만은 그대로 보낸다. 웹(nginx)을 거친 `/api` 응답도 서버가 압축한 그대로 지나간다. 그 전에는 압축이 없어 라이딩 샘플(`every=1`) JSON이 수백 KB 그대로 나갔다

## OpenData 가져오기
`./gradlew importOpenData --args="--zip <선수 zip> --index <ride index json> --name <이름> [--label cp|ftp]"`: 짝지어진 파워 라이딩을 활동으로 넣고 `cp_setting`(또는 FTP 라벨) 변화를 `athlete_threshold`에 넣는다. 화면 데모와 3단계 입력에 쓴다.

# AI가 만든 코드를 검증한 기록

이 프로젝트는 Claude Code와 Codex로 개발한다. 두 도구가 만든 코드는 아래 네 관점으로 검증하고, 기능(커밋 단위)마다 무엇을 어떻게 확인했는지와 검증에서 잡힌 실수를 남긴다. 만든 쪽과 검토하는 쪽은 나눈다.

| 관점 | 확인 방법 |
|---|---|
| 동작 | 단위·통합 테스트, 완료 기준 명령을 다시 실행 |
| 예외 | 빈 입력, 손상된 파일, 범위를 벗어난 값(음수·3000 W 초과 파워), 불규칙한 기록 간격 |
| 보안 | 입력 크기·형식 제한, 경로·SQL 주입, 인증, DAST(OWASP ZAP) |
| 데이터 정확성 | 외부 구현(GoldenCheetah)이 계산한 값과 대조, 손으로 계산한 작은 예제 |

## 기록

### 2026-10-10 0단계: OpenData 표본 추출 (`ml/src/ride_insight_ml/opendata.py`)
- **만든 것**: Claude Code. OSF 목록 → 선수 표본(해시 순서) → 다운로드(SHA-256 검증) → 인벤토리 → 선수 단위 분할
- **검증**: 단위 테스트(분할 비율, 표본의 순서 독립성, 가짜 zip 인벤토리). 실제 OSF 목록(6,613명)으로 표본 800명을 뽑아 분할 분포를 확인
- **잡은 실수**: 표본 순서와 분할이 **같은 SHA-256**을 써서, 해시 순서 앞쪽 800명이 전부 `train`으로 들어갔다(dev·test 0명). 분포를 출력해 보고 발견했고, 해시에 용도 접두어(`sample:`, `split:`)를 붙여 분리한 뒤 "표본이 세 분할에 모두 퍼지는지" 테스트를 추가했다. 테스트만 통과한 것을 믿었으면 모델 평가 전체가 무효가 될 버그였다
- **사람이 정한 것**: 표본 크기 800명·파일 80 MB 이하(12.4 GB), 분할 60/20/20(실제 475/167/158), 선수 단위 분할

### 2026-10-10 1단계: 지표 구현 (`server/.../metrics/*.kt`, `tools/ParityTool.kt`, `ml/.../rides.py`)
- **만든 것**: Claude Code. GoldenCheetah 소스(Coggan.cpp, AddIntervalDialog.cpp의 findPeaks)를 읽고 NP·IF·TSS·MMP를 Kotlin으로 옮김. 라이딩↔CSV 매핑은 Python
- **검증**
  - 동작: 손으로 계산한 작은 예제 단위 테스트 17개(창 시작 0 채움, 기록 간격별 창 크기, 틈이 있는 라이딩의 eviction, 3000 W 가드, 빈 입력)
  - 데이터 정확성: 표본 밖 선수 1명(라이딩 429개)의 GC 값과 대조 → NP 100% 일치(최대 차이 0.04 W), MMP 99.1%, TSS 78%
  - 예외: 짝지어진 라이딩이 없는 입력에서 분석 스크립트가 KeyError로 죽음 → 분명한 오류 메시지로 바꿈
- **잡은 실수**
  - (AI의 테스트 기대값 오류) MMP 틈 테스트에서 "4개 샘플 모두가 한 창에 든다"고 기대했지만 GC 규칙상 창의 지속 시간은 [N, N + 간격) 안이어야 해서 3개만 든다. 구현이 아니라 테스트의 기대값이 틀렸음을 GC 소스로 확인하고 테스트를 고침
  - (AI의 가설 설계 오류) H3가 TSS를 `cp_setting`으로 계산해 비교하도록 적었지만, GC는 IF·TSS에 존 설정의 FTP를 쓸 수 있어 `cp_setting`과 다를 수 있었다. 불일치 92건 중 88건이 이 때문이었고 IF 역산으로 확인했다. 구현을 고치지 않고 규칙 변경 2로 비교 기준을 바로잡고, 이 차이 자체를 3단계 라벨 정의의 재료로 남겼다
  - (데이터) 수동으로 받은 zip의 파일 이름을 줄여 둬서 도구가 선수를 못 찾았고(0건), 분석 스크립트는 빈 입력에서 죽었다. 둘 다 고침
  - (데이터) GC 내보내기 JSON 한 건이 `"sport":""3.5-4.5 hours""`로 깨져 있었다(사용자가 입력한 문자열을 이스케이프하지 않음). 실패 시 한 번 수리해 다시 읽도록 함
- **Codex 독립 검토 (2026-10-10, 읽기 전용, gpt-6.1-sol)**: 1차 실행은 Codex 샌드박스 초기화 오류(`helper_unknown_error: setup refresh had errors`)로 코드를 읽지 못했고, 2차는 로컬 명령(pytest·gradle)은 같은 오류로 못 돌렸지만 공개 저장소의 커밋을 읽어 정적으로 검토했다. 보고서 `work/relay/2026-10-10-1735-stage1-review-retry-codex.md`. 지적 10건과 반영:
  1. (P1) 후속 조치 규칙이 "봉인에서 기각되면 고치고 봉인을 다시 잰다"여서 봉인 결과에 맞춰 고치는 것을 허용 → 규칙을 "봉인 결과는 최종, 사후 수정은 개발 세트에서만 따로 보고"로 고침
  2. (P2) CSV의 `NaN`·`Infinity`가 `toDoubleOrNull`을 통과해 NP에 전파되거나 `RideSamples`에서 예외 → 유한하지 않은 파워는 결측(0), 유한하지 않은 secs는 깨진 행. 테스트 추가
  3. (P2) 검증에 실패한 기존 zip이 남아 inventory에 들어갈 수 있음 → SHA가 다른 기존 파일은 `.bad`로 옮기고 받기 실패 시 종료 코드 2
  4. (P2) inventory가 표본 밖 zip도 포함 → `--sample`로 매니페스트의 선수만 집계
  5. (P2) NP의 GC 0 ↔ null 비교 규칙 누락 → "GC 0은 모든 지표에서 없음"으로 규칙에 명시(분석 코드는 이미 그렇게 동작)
  6. (P2) recIntSecs 추정에서 0 간격 제외·반올림 처리 미명시 → 규칙에 적음
  7. (P2) H4의 차이 판정 방법 미명시 → 분석 코드에 이미 있던 방법(독립 재표집 차이 구간, 5%p 기준)을 규칙에 적음
  8. (P2) CSV 크기 제한 없음 → Kotlin 리더에 행 수 상한(기본 1,000,000) 추가, Python은 마지막 행만 유지하도록 바꿈
  9. (P2) `average_power="Infinity"`가 양수로 인정됨, CP 변경 횟수를 저장 순서로 셈 → 유한하지 않은 값은 None, 날짜순 정렬 뒤 셈. 테스트 추가
  10. (P3) TSS KDoc의 GC `count` 설명 오류(계산식은 맞음) → 주석 수정
  - 제안한 경계 테스트(첫 샘플이 최고, 단일 샘플, 중복 시각, 1.26초 간격, 정확히 3000 W)를 추가했다. 중복 시각은 GC와 같은 결과(합이 됨)를 내므로 구현은 두고 CSV 리더가 중복 행 수를 세서 보고하게 했다
- **개발 세트 측정 뒤 분류(2026-10-10)**: TSS 불일치 210건을 원인별로 나눴다. 170건은 GC TSS가 정수(50.0, 67.0 등)인 수동 입력, 745건(불일치가 아니라 "GC에 TSS 없음"으로 집계됨)은 GC가 IF만 저장하고 TSS를 저장하지 않은 라이딩. 둘 다 계산 차이가 아니어서 규칙 변경 3·4로 비교에서 빼고 수를 보고하게 했다. 구현을 고친 것은 없다
- **남은 불일치**: 타임스탬프가 1.00·1.03초로 흔들리는 파일 4건은 GC의 recIntSecs(1.0325, 1.0163으로 역산)를 CSV에서 복원할 수 없어 MMP·TSS가 1.6~3.3% 어긋난다. 고치지 않고 불일치로 센다

### 2026-10-10 FIT 디코더 (`server/.../fit/FitDecoder.kt`, `FitProfile.kt`, `FitActivity.kt`)
- **만든 것**: Claude Code. Garmin FIT SDK의 라이선스(내부 업무 목적, 기밀 유지) 때문에 공개 프로토콜 설명과 python-fitparse(MIT)의 프로필 번호를 참고해 직접 구현. 헤더, 정의·데이터 메시지, 압축 타임스탬프 헤더, 개발자 필드, CRC-16, 체인 파일
- **검증**: python-fitparse로 샘플 9개를 디코딩한 기대값 JSON(`server/src/test/resources/fit/expected/`, 레코드 31,156개의 timestamp·power·hr·cadence·distance·speed·altitude와 세션 요약)과 1e-6 안에서 전부 비교하는 테스트. 손상 파일 2개는 `FitDecodeException`만 내는지, 임의 텍스트·빈 입력, CRC 변조 확인
- **잡은 실수** (둘 다 대조 테스트가 잡았다. 단위 테스트만으로는 못 잡는 종류다)
  1. 세션의 `threshold_power` 필드 번호를 112로 적었는데 fitparse 프로필은 45다. Edge810 파일의 FTP 315가 null로 나와 발견
  2. 개발자 필드 정의를 필드당 2바이트로 읽었다(실제 3바이트: 번호, 크기, 개발자 데이터 인덱스). Wahoo ELEMNT 파일에서 29번째 메시지부터 어긋나 "정의되지 않은 로컬 타입 1" 오류. 같은 논리를 Python으로 다시 써서 어디서 어긋나는지 찍어 찾았다
- **설계 판단**: 활동+설정이 이어진 체인 파일은 모두 읽고, 뒤에 남은 바이트가 올바른 FIT 헤더가 아니면 오류로 본다(fitparse도 이 파일을 거절한다). 중복 시각·개발자 필드 수는 보고용으로 센다
### 2026-10-10 2단계: 저장·API (`server/.../storage`, `service`, `api`, `V1__init.sql`)
- **만든 것**: Claude Code. `docs/api.md`의 완료 기준을 먼저 적고 구현. JdbcClient + Flyway, 배열 컬럼, FIT 업로드부터 지표 저장까지, 훈련 부하, 기간 파워 커브, OpenData 가져오기
- **검증**: Testcontainers(PostgreSQL 16)에서 API 통합 테스트 6개(검증 실패 400, 종목 거절 422, 손상 파일 400, 중복 409, 없는 선수 404, 페이지네이션, 샘플 간격·상한, FTP 변경 후 TSS 재계산이 1/FTP² 비율로 맞는지, 훈련 부하가 그날 TSS와 같은지, 삭제 후 404, health UP). 업로드한 Edge810 라이딩의 NP·TSS·20분 MMP가 순수 함수 계산과 1e-3 안에서 같고, 기기(Garmin)가 세션에 적은 값과도 NP 300.6 vs 301, TSS 118.9 vs 118.7, IF 0.954 vs 0.956으로 가깝다(판정 없이 보고)
- **잡은 실수**
  - (컴파일) `JdbcClient.params(vararg Any)`에 Kotlin null 인자를 넘길 수 없음 → `params(listOf(...))`. `IntArray.mapNotNull` 없음
  - (런타임, 통합 테스트가 잡음) PgJDBC는 `float4` 컬럼을 `getObject(col, java.lang.Double::class.java)`로 읽지 못해 선수 조회가 전부 500 → `getDouble` + `wasNull` 도우미로 바꿈. 단위 테스트로는 못 잡고 실제 DB로만 잡히는 종류
  - (테스트 클라이언트) `MultipartBodyBuilder`가 reactive-streams를 요구해 `NoClassDefFoundError` → `MultiValueMap` + `HttpEntity`로 업로드
  - (AI의 테스트 가정 오류) FTP 변경 재계산 테스트에 Edge 500 파일을 썼는데 그 파일에는 파워가 없어 재계산 0건. fitparse 기대값으로 파워 유무를 확인하고 ELEMNT 파일로 바꿈
- **사람이 정한 것**: JPA 대신 JdbcClient, 시계열을 배열 컬럼에 저장, FTP는 날짜별 이력 테이블, 거절하는 종목 목록(러닝·수영·걷기·하이킹), 1~2단계에서 인증 없음(5단계에서 결정)
- **아직 안 한 완료 기준**: `docker compose up`으로 서버까지 뜨는 것(5단계에서 Dockerfile과 함께), OpenData 선수 가져오기 실측(DB를 띄운 뒤)
- **실제 실행(2026-10-10 저녁)**: `bootRun`(compose 지원으로 postgres:16 자동 기동) + Vite 개발 서버로 데모 선수에 샘플 FIT 7개 업로드(사이클링 5개 201, 러닝 422, 손상 400), OpenData 선수 1명 가져오기(활동 516, FTP 임계값 16개), 화면에서 목록·상세·대시보드 확인. bootRun은 `springBoot.mainClass`를 지정해야 했다(tools 패키지의 main 함수 둘과 충돌)

### 2026-10-10 3단계: FTP 추정 (`ml/src/ride_insight_ml/ftp.py`, `ftp_export.py`, `server/.../metrics/LightGbmModel.kt`)
- **만든 것**: Claude Code. 예측 단위 생성(28일 간격 기준일, 42일 창, 라벨 L_FTP/L_CP, 신선도), 후보 7개, 선수 단위 부트스트랩, 보고서. LightGBM JSON을 Kotlin에서 순회하는 추론기와 Python 예측 대조 테스트
- **검증**: 합성 라이딩(FTP가 100일째에 20 W 오르는 선수 12명)으로 라벨·신선도·분할이 의도대로 나오는지 단위 테스트. 정확한 2변수 곡선에서 CP 적합이 1e-6 안에서 복원되는지. 부트스트랩이 선수 단위인지(선수 2명이면 구간이 양 끝에 닿아야 함). Kotlin 트리 순회는 결측값이 섞인 합성 모델의 Python 예측 100개와 1e-6 안에서 일치
- **잡은 실수**
  - 규칙 후보(R1 등)도 "train 50개 미만이면 건너뜀"을 적용해 작은 합성 데이터에서 R1이 빠지고 KeyError → 규칙은 학습이 필요 없으므로 최소 train 조건을 0으로
  - 합성 테스트의 TSS 값이 NP·CP와 일관되지 않아 규칙 변경 2 뒤 테스트가 깨짐(테스트 데이터의 가정 오류)

- **사람이 정한 것**: 채택 후보는 dev MAE 최소(M2가 M1을 0.008 W 차로 이김)로 정하고 test를 보고 바꾸지 않음. H5 판정 불가라 서비스는 규칙 R1을 쓰고 오차를 화면에 표시. 모델을 넣지 않은 이유를 README에 적음

### 2026-10-10 5단계: 변조 FIT·DAST·부하
- **만든 것**: Claude Code. 테스트용 FIT 인코더(`FitWriter`)와 변조 7종 테스트, ZAP 자동화 계획·시드 생성기, 부하 스크립트, FTP 규칙(R1·R2·CP 적합)과 추정 API
- **검증**: 변조 7종이 미리 적은 상태 코드를 돌려주는지(H8, 전부 일치, 500 없음). CP 2변수 적합은 정확히 만든 곡선(CP 250, W' 20 kJ)을 1e-6 안에서 복원. 부하 30 업로드 + 20 조회에서 5xx 0
- **잡은 실수**
  - (DAST가 잡음) 존재하지 않는 경로와 지원하지 않는 메서드에 500을 돌려줬다. 통합 테스트는 "있는" 경로만 두드려서 못 잡았고, ZAP의 spider가 `/`, `/api`, `/robots.txt`를 두드려 잡았다. 예외 처리기의 catch-all이 프레임워크의 404·405 예외까지 삼킨 것이 원인. 404·405·415·400 매핑과 테스트 추가

# 측정 규칙과 결과

후보와 판정 규칙을 재기 전에 적고 커밋한다. 결과는 같은 절 아래에 날짜와 커밋을 붙여 추가한다. 규칙을 바꾸면 "규칙 변경" 절에 이유와 시점을 남긴다.

## 공통
- 데이터: GoldenCheetah OpenData 표본 800명(`manifests/opendata_sample.json`, 선수 id의 SHA-256(`sample:` + id) 순서로 80 MB 이하 파일 중 앞 800개). 선수 분할은 SHA-256(`split:` + id)로 train 60 / dev 20 / test 20
- 선수 단위 분할. 같은 선수의 라이딩은 한 세트에만 있다
- 불확실성: 선수 단위(또는 라이딩 단위, 절마다 명시) 부트스트랩 95% 구간, 2,000회, seed 0. 두 방법의 비교는 같은 단위끼리 짝지은 부트스트랩
- 판정은 미리 적은 가설의 "지지 / 기각 / 판정 불가(구간이 기준을 걸침)" 세 가지로만 말한다
- 봉인 세트는 단계가 끝날 때 정해 둔 것만 한 번 잰다. 봉인 세트 수치를 보고 코드·규칙을 고치지 않는다
- (2026-10-29 추가, 규칙 변경 15) 봉인 세트를 잴 때는 dev 보고서와 채택 후보(후보를 고르는 단계라면)를 먼저 커밋·push한 뒤 봉인 세트를 재고, 그 결과는 별도 커밋으로 올린다. 그래야 '채택 후보를 정한 뒤 봉인 세트를 한 번 쟀다'는 순서가 공개 이력에 남는다
- (2026-10-29 추가, 규칙 변경 16) 앞으로 등록하는 비율 가설(일치율·포함률처럼 라이딩이나 예측 단위를 세는 비율)은 선수 단위 구간으로 판정한다. 같은 선수의 라이딩·단위는 서로 독립이 아니기 때문이다. 라이딩 단위 구간은 필요하면 함께 보고만 한다. 지난 판정은 그대로 둔다(1단계 '사후 보고: 선수 군집 부트스트랩')

## 1단계: 지표 구현의 정확성 (2026-10-10 규칙, 측정 전)

### 질문
직접 구현한 NP·IF·TSS·MMP(N초 최대 평균 파워)가 같은 초 단위 CSV로 GoldenCheetah가 계산해 둔 메타데이터 값과 일치하는가. 어긋나면 어떤 라이딩에서 어긋나는가.

### 구현 기준 (GoldenCheetah 소스에서 확인한 것, 2026-10-10)
- NP(`coggan_np`): 창 크기 = `30 / recIntSecs`(정수 나눗셈). 창이 1 이하이면 0. 0으로 채운 버퍼에서 시작해 처음 30초를 빼지 않는다. 창 평균의 4제곱을 모든 샘플에서 평균한 뒤 4제곱근. 0 W 샘플도 포함
- IF(`coggan_if`) = NP / CP, TSS(`coggan_tss`) = NP × 샘플 수 × recIntSecs × IF / (CP × 3600) × 100. CP는 그 라이딩의 `cp_setting`
- MMP(`Ns_critical_power`, `findPeaks`): 시간 순서의 샘플 창을 유지하며, 창의 지속 시간 = 마지막 secs − 첫 secs + recIntSecs 가 N 이상이 되면 후보. 평균 = 샘플 합 × recIntSecs / 지속 시간. 라이딩 전체 길이(마지막 secs + recIntSecs)가 N보다 짧으면 값 없음. 평균이 3000 W 이상이면 0
- recIntSecs는 라이딩마다 하나다. CSV에는 없으므로 **연속 샘플 간격의 최빈값**(소수 둘째 자리 반올림)으로 추정한다. 이 추정이 GC와 다를 수 있다는 것이 4번 질문의 한 축이다

### 데이터
- **라이딩↔CSV 매핑** (2026-10-10 확인): 메타데이터 `date`는 UTC, CSV 파일명은 기기 현지 시각이라 이름이 그대로 맞는 라이딩은 일부다(첫 선수 203/731). 매핑 규칙: 파일명 시각과 `date`의 차이가 ±14시간 안의 15분 배수이고, CSV 마지막 `secs`가 `workout_time`과 60초 또는 2% 안에서 맞는 CSV가 **정확히 하나**일 때만 짝짓는다. 후보가 둘 이상이면 "모호"로 두고 쓰지 않는다. 라이딩의 `data` 플래그 문자열 4번째 글자가 `P`면 파워가 있는 라이딩이다. 구현은 `ml/src/ride_insight_ml/rides.py`, 매핑 결과(짝지은·모호·미매칭 수)는 결과와 함께 보고한다
- **파리티-개발**: 표본 순서(`manifests/opendata_sample.json`)로 train 선수 중 **짝지어진 파워 라이딩**이 50개 이상인 앞 100명(규칙 변경 1). 구현을 맞추는 데 쓴다. 목록은 `manifests/parity_dev.txt`
- **파리티-봉인**: 그다음 100명(`manifests/parity_sealed.txt`). 단계 끝에 한 번만 잰다
- 라이딩 조건: 짝지어진 CSV가 있고 `P` 플래그가 있는 것. GC 값이 없는 지표(None)는 "둘 다 없음"이면 일치, 한쪽만 있으면 불일치로 센다. **GC 값 0은 모든 지표에서 "없음"으로 본다**(PeakPower는 결과가 없을 때와 3000 W 이상일 때, IsoPower는 창이 1 샘플 이하일 때 0을 쓴다; 2026-10-10 소스 확인으로 측정 전에 덧붙임. Codex 검토 지적 5)
- 기록 간격(recIntSecs) 추정: 연속 샘플 간격 중 **0보다 큰 것만** 소수 둘째 자리로 반올림(반올림은 0.5 올림)한 값의 최빈값. 동률이면 짧은 쪽. 간격이 1.00인 라이딩만 "1초"로 분류한다. 최빈값의 비율(전체 양수 간격 중 최빈값인 비율)이 0.9 미만이면 "흔들리는 타임스탬프"로 보고한다
- CSV 읽기: `secs`가 없거나 유한하지 않거나 직전 행보다 작은 행은 버리고 "깨진 행"으로 센다. 같은 시각이 반복된 행은 GC처럼 그대로 쓰되 "중복 행"으로 센다. 파워가 비었거나 유한하지 않으면 0으로 두고 결측으로 센다(Codex 검토 지적 2)

### 가설 (파리티-봉인에서 판정)
- **H1 NP**: 기록 간격이 1초인 라이딩에서 |NP − coggan_np| ≤ 1.0 W 인 비율이 99% 이상이다
- **H2 MMP**: 기록 간격이 1초인 라이딩의 (라이딩, 구간 16개) 쌍에서 |MMP − GC| ≤ 1.0 W 인 비율이 99% 이상이다
- **H3 TSS**: 기록 간격이 1초이고 GC의 IF가 있고 GC TSS가 0이 아니며 정수가 아닌 라이딩에서(규칙 변경 3·4), GC가 쓴 임계값(`coggan_np / coggan_if`, 규칙 변경 2)으로 계산한 |TSS − coggan_tss| ≤ 0.5 인 비율이 99% 이상이다
- **H4 간격 강건성**: 기록 간격이 1초가 아닌 라이딩(5초, 1.26초 등)의 NP 일치율(≤ 1.0 W)은 1초 라이딩보다 5%p 이상 낮다
- 비율의 구간은 라이딩 단위 부트스트랩(2,000회, seed 0). "99% 이상"은 구간의 하한이 99% 이상이면 지지, 상한이 99% 미만이면 기각. H2는 라이딩을 다시 뽑고 그 라이딩의 16쌍을 모두 세는 라이딩 단위 재표집
- H4는 두 비율의 **차이**(1초 일치율 − 그 외 일치율)를 각 그룹을 독립으로 다시 뽑은 부트스트랩으로 구간을 내고, 하한이 5%p 이상이면 지지, 상한이 5%p 미만이면 기각, 그 외는 판정 불가. 1초가 아닌 라이딩이 없으면 판정 불가(Codex 검토 지적 7)

### 미리 정한 후속 조치
- 개발 세트에서는 어긋난 라이딩을 분류(결측 패턴, 간격 추정 오류, 3000 W 초과, 길이)해 구현을 고칠 수 있다. **봉인 세트의 결과는 1단계의 최종 결과이며, 봉인 결과를 보고 구현이나 규칙을 고치지 않는다.** 봉인 측정 뒤에 발견한 버그를 고치면, 고친 구현의 수치는 개발 세트에서만 다시 재서 "사후 수정"으로 따로 적고, 원래 봉인 결과는 그대로 남긴다(Codex 검토 지적 1로 2026-10-10 측정 전에 고침. 원래 문장은 "기각이면 구현을 고치고 봉인 세트를 고친 뒤 한 번만 다시 잰다"였는데, 이는 봉인 결과에 맞춰 고치는 것을 허용했다)
- H4가 지지되면 2단계 저장 시점에 1초 격자로 다시 맞추는 전처리(선형 보간, 5초 간격은 값 반복)를 넣고, 그 전처리를 거친 값의 일치율을 **보고만** 한다(GC는 다시 맞추지 않으므로 일치가 목표가 아니다)

### 보고할 것 (판정 없음)
- 간격별 라이딩 수, 파워 결측 비율 분포, 3000 W 초과 샘플이 있는 라이딩 수, 지표별 차이의 분포(중앙값, p95, 최대)
- GC가 IF에 쓴 임계값이 `cp_setting`과 1 W 넘게 다른 라이딩 비율(규칙 변경 2). 3단계 라벨 정의에 쓴다
- 타임스탬프가 흔들리는 라이딩 수(연속 간격의 최빈값이 전체의 90% 미만인 라이딩)
- 어긋난 라이딩 예시 5개와 원인

### 사후 수정 재측정 계획: 비교 규칙의 0 처리 (2026-10-13 등록, 측정 전)
- **바뀐 것**: 일치 판정 함수(`ml/src/ride_insight_ml/parity.py`의 `agree`)는 GC 쪽 0만 "없음"으로 보고 우리 쪽 0은 값으로 봤다. 우리 Kotlin 구현도 GoldenCheetah처럼 평균이 3000 W 이상인 MMP를 0으로 내므로(`MeanMaximalPower.peakPower`), 두 구현이 똑같이 가드에 걸려 둘 다 0인 쌍이 "한쪽만 없음"이 되어 불일치로 세어졌다. 우리 쪽이 0이고 GC 값이 없는 쌍도 불일치였다. 수정 뒤에는 양쪽 모두 0을 "없음"으로 본다(규칙 변경 9). 우리 값이 0이고 GC 값이 1 W(TSS는 0.5)보다 큰 쌍은 전과 같이 불일치다. 반대 방향 변화도 하나 있다: 우리 0과 GC의 0 초과 1 W 이하 값(TSS는 0.5 이하)은 수정 전에는 차이가 작아 일치였고 수정 뒤에는 "한쪽만 없음"이라 불일치다. Kotlin 지표 구현과 라이딩별 JSONL은 바뀌지 않았다

## 3단계: FTP 추정 (2026-10-10 규칙, 측정 전)

### 질문
최근 6주의 라이딩만 보고 선수가 설정해 둔 FTP를 얼마나 가깝게 맞히는가. 전통 규칙과 학습 모델 중 어느 쪽이 처음 보는 선수에게 더 잘 맞는가. 라벨(선수 설정값)의 신선도에 따라 결과가 어떻게 달라지는가.

### 데이터
- 표본 800명 전체의 짝지어진 파워 라이딩. 라이딩별 특징은 1단계와 같은 Kotlin 도구(`parity` 태스크)로 계산한 **우리 구현의** NP·MMP 16구간(GC 값이 아니라)을 쓴다. 분할은 공통 규칙(선수 단위 train/dev/test)
- **예측 단위 = (선수, 기준일)**. 기준일은 선수의 파워 라이딩 날짜 중 28일 간격으로 뽑는다(첫 라이딩부터 28일씩 건너뛰며 그 뒤 첫 라이딩 날짜). 창 = 기준일 포함 직전 42일. 창 안에 파워 라이딩이 8개 미만이면 뺀다
- **특징**: 창 안 라이딩의 구간별 최대 MMP 16개(W), 라이딩 수, 총 시간(h), NP 평균, 최대 NP, 마지막 라이딩까지 일수(2026-10-29 덧붙임: 기준일이 창의 마지막 라이딩 시각이라 구성상 모든 단위에서 0이었다, 규칙 변경 15), 성별, 기준일의 나이(출생 연도 있을 때), 체중(그 라이딩의 `athlete_weight` 중 마지막 값, 있을 때). 체중당 특징(W/kg)은 체중이 있을 때만 추가 변형(M1b)으로 쓴다
- **라벨**
  - 주 라벨 **L_FTP**: 창의 마지막 파워 라이딩에 GC가 IF에 쓴 임계값(`coggan_np / coggan_if`, 반올림). 없으면 그 라이딩의 `cp_setting`. 둘 다 없으면 예측 단위를 뺀다. 1단계에서 GC가 IF·TSS에 쓴 값이 CP가 아니라 존 FTP였던 라이딩이 10%였으므로, 사용자가 "FTP"로 둔 값에 더 가까운 쪽을 주 라벨로 한다
  - 보조 라벨 **L_CP**: 같은 라이딩의 `cp_setting`. 주 라벨과 다른 비율과 그때의 결과를 보고한다
  - **신선 라벨 부분 집합**: 기준일 전후 28일 안에 L_FTP 값이 바뀐 예측 단위(사용자가 최근에 FTP를 갱신함). 나머지는 "묵은 라벨"
- 라벨이 50 W 미만이거나 600 W 초과면 뺀다(입력 오류)
- 창 안에 20분 이상 라이딩이 없어 20분 MMP가 없는 예측 단위는 모든 방법에서 뺀다(R1·R3가 정의되지 않음). 뺀 수를 보고한다. R2(60분)가 없는 단위는 R2에서만 빠지고 "적용 비율"로 보고한다(2026-10-10, 측정 전 덧붙임)

### 후보
| 이름 | 방법 | 자유 매개변수 |
|---|---|---|
| R1 | 창 안 20분 MMP 최대 × 0.95 | 없음 |
| R2 | 창 안 60분 MMP 최대 | 없음 |
| R3 | CP 2변수 모델: 3·5·8·10·20분 최대 MMP에 대해 일(W×초) = CP×초 + W' 최소제곱 → CP | 없음 |
| R5 | R1을 train에서 선형 보정(a×R1 + b, 최소제곱) | train에서만 적합 |
| M1 | LightGBM 회귀. 매개변수는 미리 고정: num_leaves 15, learning_rate 0.05, n_estimators 400, min_child_samples 50, subsample 0.8, colsample_bytree 0.8, seed 0 | train으로 학습 |
| M1b | M1 + 체중당 특징 (체중 있는 단위만) | train |
| M2 | Ridge 회귀(α = 1), 입력은 log(MMP)와 나머지 특징 표준화 | train |

R4(CP 3변수)는 돌리지 않는다. 비선형 적합이 필요하고 FTP 추정 정확도에서 R3보다 낫다는 근거가 약해 비용 대비 얻는 것이 적다고 판단했다(측정 전 결정).

### 지표와 판정
- 지표: MAE(W), 중앙값 절대 오차, MAPE, 편향(예측 − 라벨 평균). 구간은 **선수 단위** 부트스트랩(2,000회, seed 0). 두 방법 비교는 같은 선수끼리 짝지은 부트스트랩
- 후보 고르기: dev에서 L_FTP MAE가 가장 낮은 방법을 **채택 후보**로 정한다. 그다음 test에서 한 번만 잰다
- **H5**: 채택 후보의 test MAE는 R1보다 5 W 이상 낮다(짝지은 차이 구간 하한 ≥ 5 W → 지지, 상한 < 5 W → 기각)
- **H6**: R1은 L_FTP를 평균적으로 과대 추정한다(편향의 구간 하한 > 0 → 지지)
- **H7**: 신선 라벨 부분 집합에서 채택 후보의 MAE는 묵은 라벨보다 5 W 이상 낮다(독립 부트스트랩 차이, 하한 ≥ 5 → 지지, 상한 < 5 → 기각)
- 보고(판정 없음): L_CP로 바꿔 잰 MAE, 성별·연대별 MAE, 창 안 라이딩 수에 따른 MAE, 예측 단위 수와 선수 수, 라벨이 L_FTP/L_CP 다른 비율

### 서비스 반영 (미리 정한 규칙)
- H5가 지지되면 채택 후보를 서버에 넣는다. LightGBM이면 `booster.dump_model()` JSON을 내보내 **Kotlin에서 트리를 직접 순회**해 추론하고(새 의존성 없음), Python 예측과 dev 100개 단위에서 1e-6 안에 같은지 테스트한다. 선형 모델이면 계수를 그대로 넣는다

- 어느 쪽이든 추정 API는 추정값과 함께 근거(창 안 라이딩 수, 20분·60분 최대, 신뢰 구간 대신 dev MAE)를 돌려준다
- (2026-10-24 덧붙임, 규칙 변경 14, 기록만) 위 dev MAE와 함께 보여 주는 봉인 test MAE·편향은 측정 조건(6주 창, 창 안 파워 라이딩 8개 이상) 안의 응답에만 붙인다. 조건 밖(12·52주 창, 라이딩 8개 미만)의 오차는 재지 않았으므로 재지 않았다고만 안내한다

### R1 조건부 80% 예측 구간 (2026-10-30 규칙, 측정 전)
3단계 서비스 반영 규칙은 추정값과 함께 '신뢰 구간 대신 dev MAE'를 돌려주기로 했다. 당시의 선택이고 구간을 기각한 것은 아니다. MAE 한 숫자로는 오차가 어느 쪽으로 얼마나 퍼지는지, 그것이 조건마다 다르다는 것을 보여 줄 수 없다. 이 절은 R1에 창 안 라이딩 수 구간별 80% 예측 구간을 붙이는 방법을 train으로 보정하고 dev로 확인하는 규칙이다(규칙 변경 18).

- **먼저 본 것(사후 성격)**: 2026-10-19 읽기 전용 코드 검토가 예측 단위 파일의 dev 단위(20분 MMP가 있는 1,522개)로 다음을 먼저 계산해 봤다(train·test는 쓰지 않음). R1 − L_FTP의 분위 10% −55.5 W, 50% −15.4 W, 90% +24.9 W. 지금 안내의 dev MAE를 대칭 구간 R1 ± 31 W로 읽으면 포함률 60.6%. 창 안 라이딩 수 구간별 R1 − L_FTP 중앙값·MAE(8~12개 −32.1·42.6 W, 13~20개 −22.2·31.6 W, 21~30개 −11.0·27.5 W, 31개 이상 −5.0·24.2 W). 신선/묵은 라벨별 10%·90% 분위(−37.5/+13.2 W, −58.1/+28.1 W). dev 자체의 10%·90% 분위로 만든 구간(폭 80.4 W, 같은 dev에서 포함률 79.9%). 그래서 아래 dev 확인은 dev 잔차 분포를 본 뒤의 확인이다. train으로 보정한 구간의 dev 포함률은 계산하지 않았다. 라이딩 수 구간 4개는 3단계 집단별 보고(2026-10-10)의 구간을 그대로 쓴다
- **데이터**: 3단계 예측 단위 파일(`data/features/units.parquet`, `reports/ftp/build.json`과 같은 8,093단위)을 그대로 쓴다. 20분 MMP가 없는 단위는 3단계처럼 뺀다(train 4,970단위, dev 1,522단위). 보정 세트 = train 단위. R1은 학습할 매개변수가 없어 train 단위가 R1을 만드는 데 쓰이지 않았다(3단계에서 train은 모델과 R5 적합에만 썼다). 확인 세트 = dev 단위. 봉인 test는 3단계에서 한 번 썼으므로 이 절에서 쓰지 않는다(도구는 test 단위를 읽어도 버리고, 분할을 고르는 옵션이 없다)
- **방법 (split conformal, 라이딩 수 구간별 = Mondrian)**: 창 안 파워 라이딩 수 구간 4개(8~12, 13~20, 21~30, 31개 이상)마다 train 단위의 잔차 r = L_FTP − R1을 작은 순서로 놓고(n = 그 구간의 train 단위 수, 순서는 1부터 센다) q_lo = r(⌊0.10·(n+1)⌋), q_hi = r(⌈0.90·(n+1)⌉)로 둔다. 구간 = [R1 + q_lo, R1 + q_hi](양 끝 포함). 단위가 서로 교환 가능하면 양쪽 꼬리가 각각 10% 이하라 포함률이 80% 이상이 되는 표준 split conformal 분위다. n < 9면 이 순서 통계량이 정의되지 않으므로 그 라이딩 수 구간은 구간을 내지 않는다(그 구간의 dev 단위는 포함률에서 빼고 수를 보고한다). 같은 선수의 단위끼리는 독립이 아니어서 이 보장이 단위 수준에서 그대로 성립하지 않으므로, 포함률은 아래처럼 선수 단위로 확인한다
- **H14 (dev 참고 판정)**: dev 단위에서 L_FTP가 구간 안에 드는 비율(포함률)과 그 선수 단위 부트스트랩 95% 구간(2,000회, seed 0, 공통 절 규칙 변경 16)을 잰다. 구간이 [76%, 84%] 안에 있고(하한 ≥ 76%, 상한 ≤ 84%) 80%를 포함하면 '보정 유지', 상한 < 76% 또는 하한 > 84%면 '보정 실패', 그 밖은 '판정 불가'다. 위의 사후 성격 때문에 이 판정은 서비스에 넣을지 정하는 참고 판정이다. 정식 판정은 처음 보는 선수의 새 봉인 세트에서만 할 수 있고 그 세트는 아직 없다(만들지 않으면 이 절은 dev 참고 판정과 보고로만 남는다)
- **보고 (판정 없음)**: 라이딩 수 구간별 train 단위 수·q_lo·q_hi·폭(q_hi − q_lo), 같은 구간의 dev 단위·선수 수와 포함률(선수 단위 구간 함께), dev 단위 구간 폭의 중앙값, 신선/묵은 라벨별 포함률, 지금 안내를 대칭 구간 R1 ± 31 W(dev MAE)로 읽었을 때의 dev 포함률(위 60.6%를 같은 파일에서 다시 계산)
- **서비스 반영 (미리 정함)**: '보정 유지'일 때만 바꾼다. 6주 창이고 창 안 파워 라이딩이 8개 이상(측정 조건 안, 규칙 변경 14)이며 R1이 있는 추정 응답에 `interval80 {lowWatts, highWatts, ridesBucket, level 0.8, calibratedOn "train", devCoverage}`(devCoverage는 그 라이딩 수 구간의 dev 포함률)를 더하고, 대시보드의 FTP 추정 카드에 '개발 세트 기준 80% 구간'으로 보인다. 보정 표는 이 측정이 쓴 `reports/ftp/r1-intervals.json`이고, 서버는 같은 내용의 리소스 사본을 읽는다(서버 Docker 빌드 컨텍스트가 `server/`라 사본이 필요하고, 서버 테스트가 둘이 같은지 확인한다). 기존 오차 필드(dev·봉인 test MAE, 편향)는 API 호환을 위해 그대로 둔다. '판정 불가'·'보정 실패'면 서비스는 바꾸지 않고 보고만 남긴다
- **한계(미리 밝힘)**: 포함률은 OpenData(GoldenCheetah 사용자) 선수 기준이다. 이 서비스에 기록을 올리는 사용자는 기기·훈련 방식·FTP 설정 습관이 다를 수 있어 80%가 그대로 성립한다고 말할 수 없다(그래서 화면에 '개발 세트 기준'). 구간은 선수가 설정해 둔 FTP 값(L_FTP)이 들 범위이지 생리적 FTP의 범위가 아니다. 서비스 창과 측정 창은 정렬이 다르지만 길이가 같다(규칙 변경 14)
- **측정 명령**: `cd ml && uv run --no-sync python -m ride_insight_ml.ftp calibrate --units ../data/features/units.parquet --out ../reports/ftp/r1-intervals`(`.json`과 `.md`를 쓴다). CPU 수 초, GPU 없음

### 업로드 동시 처리 상한 (2026-10-15 규칙, 적용 전)
H11 두 번째 재측정에서 상한 가까운 파일(rich 50만, 6.5 MB) 동시 5개는 모두 201이었지만 사용 힙이 최대 511 MB(GC 뒤 461 MB)까지 올라 512 MB 한도에 여유가 거의 없었다. 상한 가까운 파일의 업로드 한 건이 아직 90 MB 남짓을 쓰고, 동시에 처리하는 수에 비례해 늘어나기 때문이다. 동시 처리 수를 묶는다(규칙 변경 12).

- **정한 것**
  1. 업로드의 디코딩·저장은 서버 전체에서 **동시에 2개까지만** 한다. 나머지는 도착 순서대로 차례를 기다리고(공정한 세마포어), **30초** 안에 차례가 오지 않으면 **429 `too_many_uploads` + `Retry-After: 5`**로 돌려보낸다. 파일 바이트는 차례를 얻은 뒤에 메모리로 읽는다(기다리는 동안 업로드는 multipart 임시 파일에만 있다). 2와 30초는 설정(`ride-insight.upload.max-concurrent`, `ride-insight.upload.max-wait-seconds`)으로 바꿀 수 있는 일상적 기본값이다: 2개면 상한 가까운 업로드도 2 × 90 MB 남짓이라 512 MB 힙에 여유가 남고, 정상 크기 업로드(1초 이내)는 거의 기다리지 않는다
  2. `compose.yaml`의 서버 서비스에 **메모리 한도 768 MB**를 둔다. 이미지는 `-XX:MaxRAMPercentage=75`라 최대 힙이 약 576 MB로, 측정에 쓴 512 MB 힙과 비슷하다(그 전에는 한도가 없어 Docker 가상 머신 메모리의 75%까지 힙이 클 수 있었다)
